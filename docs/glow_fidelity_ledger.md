# GLoW Fidelity Ledger

This ledger tracks the implemented GLoW components against the paper-facing design used in this repository. It is intentionally explicit about what exists as a first-class subsystem, what is still approximate, and where the codebase chose a practical Jericho-oriented implementation over a stronger paper-equivalent interpretation.

## Remaining Deviations

- The local and global world models are typed symbolic artifacts plus prompt-mediated analysis, not separately trained neural world models.
- Selection, reranking, commit gating, and frontier ranking remain explicit heuristics and config weights, not learned end-to-end components.
- Action generation is intentionally constrained by Jericho valid actions when available, which is practical for parser IF but stronger than a generic open-ended policy interface.
- Potential value comes from typed critical-state inference over retained trajectories, not from a separately trained potential-value estimator.
- Restore validation after native snapshot load is conservative and heuristic because Jericho does not expose a perfect inspection surface after `set_state()`.
- JSONL trajectory writing, run-scoped manifests, and the exact artifact directory layout are repo-specific implementation choices.
- The runner can preload the newest archive snapshot from its configured archive directory, but the default CLI rewrites outputs under a per-run root, so shared-archive workflows require explicit caller control rather than happening automatically across unrelated CLI runs.

## Reading This Ledger

- `implemented? = yes` means the paper-facing concept exists as a first-class subsystem in the repo.
- `known deviations` names the strongest place where the implementation still differs from a stricter paper-faithful interpretation.
- `reason for deviation` explains why that choice exists instead of implying paper-equivalence.
